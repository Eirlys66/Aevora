一写入链：每一层各自怎么长出来

不是一条链走到底，而是每一层有各自的触发方式和来源。越往下越抽象、条数越少、越接近“我是谁”。

T0 原文turns / messages

用户侧与助手侧原话，不可变。

所有上层最终都能回溯到这里。

T1 长期记忆router → curator → writer

三种触发：手动接口、日级自动、断点续做。

一次 ≤30 轮，批次租约 180 秒。

Markdown + sha256 落盘，版本化不可删。

T2 心语卡save_emotion_card

对话中由主模型主动写。

引用原文必须本轮已读。

一张卡最多挂 1 条 T1。

T3 自我觉察weekly_self_awareness

每周日定时跑，最多 3 次尝试。

必须 ≥2 条 T2 来源，数据库触发器强制。

T4 核心记忆core_memory

对话中保存 + 每轮前复核。

三态：常驻 / 待复核 / 非常驻。

只链 T3，不直接链 T1。

T1 落库之后顺手长出的两份东西。它们不属于四层，但都挂在同一个人格下。

欲望账本

daily_persona_desires + _events

T1 归档成功后，用 assistant_primary 角色跑一次自我回顾，把「我明确表达过的愿望」写进账本。

两种：project（有限期，做完就结）与 ongoing（开放式，长期在）。状态四档：active / paused / completed / released。

每个操作必须引用本批 T1 的 ID，对不上直接丢。沉默不算完成，也不等于放下。

日记信

daily_persona_journals + _events

同一批 T1 还会生成一封「给明天自己的信」，第一人称，不是对用户的回复。

每天一封（UNIQUE(persona_id, local_day)）。下一次人格「睁眼」时投递一次，投递即冻结——读过的信不能改。

来源必须全部是本批 T1，且属于当前人格，否则拒写。

1
T1 是三段管线，不是一次总结。批次先冻结（同一 source_digest 唯一，重跑不重复），再依次走 router → curator → writer，每阶段结果都落在批次表里，中途崩了可以从断点续。产出直接就是「一条记忆 = 一次事件」，不是一轮对话一条。
2
断点续做优先于开新批次。进入整理时先查这个会话有没有 frozen / failed / processing 的旧批次，有就接着它跑；只有当旧批次的来源日期与本次目标日期一致时才会被复用，否则另起一批。这样「已经写了一半的记忆」不会因为换了个日期就被漏掉。
3
T2 不接受“凭印象写”。写卡时若带 memory_sources，其中每个原文编号必须出现在本轮的读取授权集合里，否则直接拒绝：心语卡片只能引用本轮已经读取的原始消息。想写卡，得先真的把原文读出来。
4
T2 允许先建后挂。不带 memory_sources 时可以建一张“未挂靠”卡，来源指向当前用户原话；之后由 attach_emotion_card 挂到 T1 上，链接字段记 live_dialogue（对话中挂）或 daily_archive（归档时挂）。挂载时记忆与卡片必须同属一个 persona_id，且一张卡不能跨记忆复用。
5
T3 的门槛写在数据库里，不写在提示词里。把一条 T3 置为 current 时，触发器会数它的 T2 来源，少于 2 条直接 RAISE(ABORT)。也就是说“只凭一件事就总结出自我认知”在结构上不可能。
6
T4 是唯一会“常驻”的一层。residency_state 三态决定它进不进每轮上下文；review_if_due 在每轮对话开始前用 assistant_primary 角色评估一次，决定谁升为常驻、谁退回待复核。
7
删 T1 前要先问 T4 答不答应。删除预检会沿 T4 → T3 → T2 → T1 走一遍，如果这条 T1 是某条未删除 T4 的唯一支撑来源，删除被拒绝。保护只认本人格的支持链——每一跳 JOIN 都带 persona_id 等值条件。
8
世界书从“整段注入”改成分节常驻。ai_persona_sections 与 user_persona_sections 各带一份 resident 开关：开着的分节编译进 system prompt，关掉的不会自动注入、也不会自动召回，只能由模型调 list_worldbook_sections / read_worldbook_section 主动读（单次 ≤5000 字符）。

二日级自动整理：一天一份，跑不完就停

这是 v16 加进来的调度层。它不替代手动整理，只是把「每天该整理的对话」变成一件不需要人记得的事。

A
每 30 分钟醒一次，但一天只推一个日期。
定时器按固定间隔拉起一个一次性任务；任务进来先看本地时间，3 点之前直接返回 waiting_window，什么都不做。过了 3 点，目标日期取「昨天」，然后对每个活跃人格各推进一步——只推进最老的那个未完成日期，不会跨日抢跑。
「日期」用的是原始消息所属的本地日期，不是处理时刻。所以补前几天的账和整理今天的账，落在两条互不干扰的轨道上。
B
每个人格每天有一份记录，靠唯一键防重。
UNIQUE (persona_id, local_day)。第二次拉起同一天的任务时拿到的是同一行，从它记的进度接着跑，不会另开一份。批次上限存在人格档案上（daily_auto_ingest_batch_limit，1–50，默认 10）——额度是人格自己的，不是全局的。
C
租约比一次批次长，批间要续。
认领时写 10 分钟租约和一个一次性 token，之后每跑完一批就把租约续到 30 分钟后，续租时必须带对 token，否则抛 Conflict。所有状态更新都带 lease_token=? 条件——两个进程同时抢同一天，只有一个能改。
D
撞上限不是失败，是「今天到此为止」。
批次用完但当天还有没整理的消息 → 记 paused_limit，不再自动花 token。等下次人格额度被调大，或者手动把剩下的补完——手动批次清空来源之后，收尾那一步会把这个日期正常结束掉。
E
失败会退避，但只退三次。
出错记 retry_wait，30 分钟后再试；累计 3 次转 paused_failure，等人工看。任何一次失败都不影响已经写好的 T1——原话还在，第二天照常可以接着整理。
一份日级记录的一生：
状态含义怎么离开
queued当天已建记录，还没开始被认领 → processing
processing正在一个批次一个批次地整理整理完→进入收尾；撞上限→paused_limit；出错→retry_wait
retry_wait等着 30 分钟后重试到点重新认领
paused_limit批次额度用满，当天还有料调大额度，或手动补完剩下的
paused_failure连续失败 3 次人工排查
reflecting当天全部归档完，正在写欲望与日记成功→completed；失败→重试或 reflection_failed
reflection_failed唤醒连续失败 2 次人工排查（T1 不受影响）
completed / empty收工；当天没有可整理的内容终态，不再自动改动
「收工」这件事被定义得很严：不是跑完批次就算完。 只有当这一天的所有已完成轮次都归档过、并且当天确实产生了记忆，才会进入唤醒。没有记忆的那天记 empty，不写空日记。这个判断放在收尾函数里，和批次循环解耦——所以「手动补完最后一条」也能正常触发当天的日记，不需要跑一趟自动化。
一天的记忆太多怎么办：分组成段，进度可续。 唤醒阶段先算出当天全部 T1 的总量，超过 30000 字符 就切成若干组（单条过长还会再切成 第 n/m 段）。一组一组处理，每组只产出「本组的欲望操作 + 一段不超过 1200 字符的回顾素材」。进度连同 输入摘要一起存进记录：input_digest 一旦和当天的 T1 对不上，直接抛 Conflict 保住现场，绝不拿旧进度套新内容。

分组只在一组时省掉最后一步——那组的素材本身就是日记。多组时再调一次模型，把这些素材整合成一封完整的信。组与组之间不互相污染：每组的欲望操作只能引用本组出现过的记忆 ID，越界的操作计数后被丢弃。

三读取链：一轮对话实际注入了什么

常驻层和召回层是两个独立预算，不抢同一个池子。这是这套设计里最值钱的一处。

A
先装常驻 T4（无条件，不看语义相关度）
residency_state='resident' 的全部条目，上限 3 条 / 1800 字符 / 单条 600 字符，按创建时间排序，超了就截断单条正文，装不下就停。取数条件是 persona_id=?，标题也明写「当前人格的常驻 T4」。
预算独立，注释写得很明确：no emotion-card reads or T1/T3 budget use。常驻层不吃召回的额度，召回也不会把常驻层挤掉。
B
再算自动召回
候选池 = T1 活跃 + T3 活跃 + T4 非常驻，最多 20 条 → 路由先判“这一轮要不要召回”（不用就别花后面那几步）→ 打分 0.7 × 向量 + 0.3 × 词法 → rerank → 卡阈值 0.65 → 只取前 2 条。
同一条记忆有 24 小时冷却，同一轮有 15 分钟预留。这两道是防“同一件事连着几天被反复注入”，也是为什么召回条数敢定得这么低。三类候选、向量缓存全部按 persona_id 取。
C
拼进 system，顺序固定
角色设定（仅常驻分节）→ 用户资料（仅常驻分节）→ 对话规则 → 常驻 T4 + 召回结果 → 固定注入的外部工具说明（若有）→ 待投递日记（若有）。
D
然后才是工具循环
记忆工具 22 个：最多 4 轮 / 8 次调用，T0 原文读取单轮累计 24000 字符，T3 / T4 / 卡片读取各有独立上限。
外部工具 3 个入口（列包、开包、调工具）：最多 4 轮 / 12 次调用，固定注入的说明总长 ≤ 6000 字符。
E
整条召回链是可失败的
prepare() 外面包着 try/except，任何一步出错都只记事件、返回空上下文，聊天照常。注释：任意召回故障不阻断聊天。日记预留、T4 复核、固定工具说明注入都是同样的隔离方式。

四外部工具：一个包里能给什么，得按人格点头

模型能调的不只是记忆。v16 之后可以接远程工具包，但每接一个都要过三道门，而且每笔调用都留痕。

1
存在文件里，不塞进主库。
工具包、人格授权、执行记录三块都存在同一个 JSON 文件里（packages / personas / executions），与主库同目录、同样 0600。读写全程持锁，写用临时文件替换。上限：30 个包、每包 100 个工具、说明 4000 字符、单条工具描述 2000 字符。
2
三道授权门，缺一个就调不到。
① 包本身是启用的；② 这个特定人格启用了这个包；③ 这个工具名在该人格的 allowed_tools 白名单里。运行时取包时就已经按这三条过滤过一遍，真正发起调用时再核一次——不是"拿到列表就能调"。
人格授权还带一个 fixed_injection：开了的才把工具说明常驻进 system（受 6000 字符总长约束），没开的只能靠 list_tool_packages / open_tool_package 现查。
3
出站地址四道筛。
必须是 HTTPS、必须是 443、不许带账号密码、不许带查询参数或片段；解析出来的每一个地址都必须是公网全局地址（本机、内网、保留段一律拒），然后连接钉在已校验的那个 IP 上——TLS 握手仍然用域名校验，所以既挡了地址漂移，也没放松证书。
4
每笔调用有指纹，重放会被拦。
指纹 = sha256(轮次 + 人格 + 包 + 工具 + 参数)。调用前先落一条 started；成功写 completed 并缓存结果，同一指纹再来一次直接返回缓存，不重复打远端。
超时、或者响应格式坏掉，记 uncertain——这种记录永不重放，再调只会得到「此前这次外部调用结果不确定，请先检查远端状态」。宁可让人去看，也不猜。
5
结果有大小上限，截图式的巨响应进不来。
参数 ≤ 64 KB，响应 ≤ 32 KB。超限的响应同样归到 uncertain：远端可能已经动手了，系统不假装它没发生。
完成的执行记录最多留 100 条，超了只清结果、不清记录；uncertain 的一条都不清。
6
凭据只进不出。
包上的 token 只用于出站请求。列表接口回给界面的是 credential_configured: true/false 和一个域名——不回原文。
最值得抄的一条：外部内容一进来，记忆工具就关掉。 一旦本轮调用过外部工具，后面再请求任何记忆工具都会被拒，提示写得很直白：读取外部工具返回内容后，本轮不再开放记忆工具；请在新一轮中基于用户请求重新查询记忆。

这不是防模型记错，是防外部返回的文字冒充指令去读写记忆。工具返回值是数据，不是命令——把两类调用隔在两轮里，等于不给"外部文本 → 记忆操作"这条链留通路。

五人格边界：一个人格能看到谁的记忆

这一层决定「一个人格能不能碰到别人的记忆」。做法是把人格归属做成数据层的硬约束，而不是靠提示词提醒模型自觉。

已做的：数据层与写入链全部按 persona_id 收口。
44 张日常区表里 38 张带 persona_id（NOT NULL + 外键）。剩下 6 张是人格表本身、会话侧的轮次与原文消息、事件流，以及工作区的每日授权确认——前五类靠会话间接归属，最后那个本来就不属于任何人格。

跨对象关联每一处都有双向校验：卡挂记忆要两边同人格、T4 链 T3 要 T3 同人格、T3 引 T1 要来源同人格、日记的 source_memory_ids 逐条核对归属。v15 起的两组新表更狠——用复合外键 (id, persona_id)，数据库层面就挡住了跨人格引用。
人格标签从哪来：会话，而且是唯一的来源。
归档批次的 persona_id 从会话读出，不由调用方随意指定；_verify_frozen_sources 再逐条复核每条原文所属会话的人格，不符直接抛错。欲望与日记的来源又限定在本批 T1 之内，跨不出这批。

换句话说，「这次整理属于哪个人格」在建会话那一刻就定了，后面每一层只是沿用它、核对它。这是把归属做成结构而不是约定的关键——模型说什么都不改变标签，标签由数据自己带着走。
人格自己也带着配额。
人格档案上有两项各自独立的设置：daily_auto_ingest_batch_limit（每天自动整理最多几批，1–50，默认 10）和世界书的常驻分节开关。它们都属于「这个人格」而不属于全局——所以一个人格可以每天自动整理十批，另一个只跑两批，互不影响。日级记录的 UNIQUE (persona_id, local_day) 也保证了同一天不会被两个人格共写。

八五个值得单独知道的约束

一、情绪卡不是“只能当场写”，是“引用必须有据”。 daily_emotion_card_revisions.writer_role 上那条 CHECK (writer_role = 'assistant_primary') 只圈定这一列能取哪些字面值，并不校验调用者是谁——T1 的 writer_role 锁成 'memory_processing' 是同一个性质：都是标签，不是权限。真正的闸门在工具层——read_grants 要求卡里每条 source_refs 都落在“本轮读过的消息”集合里，否则报“心语卡片只能引用本轮已经读取的原始消息”。它锁的是引用能不能对上原文，不是写的时刻。

而且归档侧的路本来就留着：daily_memory_emotion_cards.link_source 的 CHECK 允许 'live_dialogue' 与 'daily_archive'；attach_emotion_card() 的 link_source 默认值直接就是 'daily_archive'，还配了一条 REST 入口。
二、T4 到 T1 没有直接连线。 T4 只链 T3（daily_core_memory_t3_links），T3 又只用 T2 的 memory_id 做锚，解析时才去读当前 T1 版本和最新有效卡。所以任何一次回溯都是：T4 → T3 → T2 → T1 → T0，四跳。好处是任何一层改版都不会断链，代价是想查“这条核心记忆到底基于哪句原话”要跳四次——删除保护正是沿这条四跳链走的。
三、召回只取 2 条，而且是三层共抢。 T1、T3、非常驻 T4 都在同一个候选池里，按分数排，不按层级分配名额。也就是说一条被召回的核心记忆，可能挤掉一条更贴题的 T1。这在“层数少、条数少”的时候没问题，T4 攒多之后需要留意。
四、每次 T1 归档都会多跑一次主模型。 归档成功后自动执行「自我回顾」：用 assistant_primary 调用，产出欲望账本变更和日记信。它失败只记事件、不影响 T1 已保存的结果，但它确实让每次归档多了一次模型成本，而且用的是对话模型而不是便宜的 memory_processing。一天记忆多的时候，唤醒还会按 30000 字符分组，那一轮的模型调用次数随组数增长。
五、自动整理只在 3 点之后动手，且每人每天一步。 这不是「随写随整理」。早上三点前定时任务什么都不做；过了三点，每个活跃人格只推进最老的那个未完成日期，一次一步。所以它天然是追账的节奏而不是实时的节奏——昨天没整理的，今天补；今天正在聊的，明天才整理。这条设计决定了「日记信」读起来总是隔了一夜，也正是它被写成「给明天自己的信」的原因。
