一写入链：四层各自怎么长出来

不是一条链走到底，而是每一层有各自的触发方式和来源。越往下越抽象、条数越少、越接近“我是谁”。

T0 原文source_messages / messages

用户侧与助手侧原话，不可变。

所有上层最终都能回溯到这里。

T1 长期记忆router → curator → writer

显式接口触发，一次 ≤30 轮，租约 180 秒。

Markdown + sha256 落盘，版本化不可删。

按 topic user_profile chat_desire 三类分轨。

T2 心语卡save_emotion_card

对话中由主模型主动写。

引用原文必须本轮已读。

一张卡最多挂 1 条 T1。

T3 自我觉察weekly_self_awareness

每周日定时跑，最多 3 次尝试。

必须 ≥2 条 T2 来源，数据库触发器强制。

T4 核心记忆core_memory

对话中保存 + 每轮前复核。

三态：常驻 / 待复核 / 非常驻。

只链 T3，不直接链 T1。

1
T1 是三段管线，不是一次总结。批次先冻结（同一 source_digest 唯一，重跑不重复），再依次走 router → curator → writer，每阶段结果都落在批次表里，中途崩了可以从断点续。产出直接就是「一条记忆 = 一次事件」，不是一轮对话一条。
2
T2 不接受“凭印象写”。写卡时若带 memory_sources，其中每个原文编号必须出现在本轮的读取授权集合里，否则直接拒绝：心语卡片只能引用本轮已经读取的原始消息。想写卡，得先真的把原文读出来。
3
T2 允许先建后挂。不带 memory_sources 时可以建一张“未挂靠”卡，来源指向当前用户原话；之后由 attach_emotion_card 挂到 T1 上，链接字段记 live_dialogue（对话中挂）或 daily_archive（归档时挂）。
4
T3 的门槛写在数据库里，不写在提示词里。把一条 T3 置为 current 时，触发器会数它的 T2 来源，少于 2 条直接 RAISE(ABORT)。也就是说“只凭一件事就总结出自我认知”在结构上不可能。
5
T4 是唯一会“常驻”的一层。residency_state 三态决定它进不进每轮上下文；review_if_due 在每轮对话开始前用 assistant_primary 角色评估一次，决定谁升为常驻、谁退回待复核。

二读取链：一轮对话实际注入了什么

常驻层和召回层是两个独立预算，不抢同一个池子。这是这套设计里最值钱的一处。

A
先装常驻 T4（无条件，不看语义相关度）
residency_state='resident' 的全部条目，上限 3 条 / 1800 字符 / 单条 600 字符，按创建时间排序，超了就截断单条正文，装不下就停。
预算独立，注释写得很明确：no emotion-card reads or T1/T3 budget use。常驻层不吃召回的额度，召回也不会把常驻层挤掉。
B
再算自动召回
候选池 = T1 活跃 + T3 活跃 + T4 非常驻，最多 20 条 → 路由先判“这一轮要不要召回”（不用就别花后面那几步）→ 打分 0.7 × 向量 + 0.3 × 词法 → rerank → 卡阈值 0.65 → 只取前 2 条。
同一条记忆有 24 小时冷却，同一轮有 15 分钟预留。这两道是防“同一件事连着几天被反复注入”，也是为什么召回条数敢定得这么低。
C
拼进 system，顺序固定
角色设定 → 用户资料 → 对话规则 → 常驻 T4 + 召回结果。拼完进工具循环：最多 4 轮 / 8 次工具调用，共 19 个记忆工具。
D
整条召回链是可失败的
prepare() 外面包着 try/except，任何一步出错都只记事件、返回空上下文，聊天照常。注释：任意召回故障不阻断聊天。

五三个值得单独知道的约束

一、情绪卡不是“只能当场写”，是“引用必须有据”。 daily_emotion_card_revisions.writer_role 上那条 CHECK (writer_role = 'assistant_primary') 只圈定这一列能取哪些字面值，并不校验调用者是谁——T1 的 writer_role 锁成 'memory_processing' 是同一个性质：都是标签，不是权限。真正的闸门在工具层——read_grants 要求卡里每条 source_refs 都落在“本轮读过的消息”集合里，否则报“心语卡片只能引用本轮已经读取的原始消息”。它锁的是引用能不能对上原文，不是写的时刻。

而且归档侧的路本来就留着：daily_memory_emotion_cards.link_source 的 CHECK 允许 'live_dialogue' 与 'daily_archive'；attach_emotion_card() 的 link_source 默认值直接就是 'daily_archive'，还配了一条 REST 入口 POST …/memories/{memory_id}/emotion-cards/{card_id}；另有一张“未挂靠卡片”待办队列，超过 24 小时标 overdue。也就是说“先留卡、事后挂回某条记忆”这条链，今天的代码就是通的。

缺的是另一半：创建卡片的 create_emotion_card() 没有 REST 入口，只有对话工具那一条路（写死 link_source="live_dialogue"），而服务层本身接受 daily_archive。所以想让凌晨那批模型写卡，不用改 schema，是给它接一个入口、调用时传 daily_archive。唯一真要动 schema 的是标签诚实度——想让这批卡在库里明确标成“离线补写”，得放宽 writer_role 的枚举；那是元数据，不影响能不能写。
二、T4 到 T1 没有直接连线。 T4 只链 T3（daily_core_memory_t3_links），T3 又只用 T2 的 memory_id 做锚，解析时才去读当前 T1 版本和最新有效卡。所以任何一次回溯都是：T4 → T3 → T2 → T1 → T0，四跳。好处是任何一层改版都不会断链，代价是想查“这条核心记忆到底基于哪句原话”要跳四次。
三、召回只取 2 条，而且是四层共抢。 T1、T3、非常驻 T4 都在同一个候选池里，按分数排，不按层级分配名额。也就是说一条被召回的核心记忆，可能挤掉一条更贴题的 T1。这在“层数少、条数少”的时候没问题，但 T4 攒到十几条之后需要留意——它可能会长期占住那两个名额。
