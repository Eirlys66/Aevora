# 02 · 数据模型

16 张业务表 + 1 张元信息表（schema v5）。全部定义见 `backend/app/schema.sql`。

> 本文只覆盖**工作区**这一半。日常区那 6 张 `daily_*` 表（v4）由另一条工作线引入，
> 字段语义见 `backend/app/services/daily.py` 与 `backend/app/api/routes_daily.py`，
> 本文尚未补齐——这是文档缺口，不是没有这些表。

## meta

| 列 | 说明 |
|---|---|
| key / value / updated_at | 目前只存 `schema_version` |

## projects

| 列 | 说明 |
|---|---|
| id | `prj_<hex>` |
| name | 唯一，同时是目录名（白名单：字母数字 `._-`，长度 1-63） |
| work_root | 绝对路径，创建时落在 `AEVORA_PROJECTS_DIR` 内并已通过 realpath 校验 |
| goal / current_summary | 目标与当前概述（概述只属于工作区，不与日常区混写） |
| status | `active` / `archived` |

`work_root` 与 `name` 都加了唯一约束：同一目录不会被两个项目引用。

## tasks

| 列 | 说明 |
|---|---|
| phase | 见下方状态机 |
| current_proposal_id | 当前生效的提案版本；换版时更新 |
| goal / done_criteria | 任务目标与完成条件 |

状态机：

```
discussion ──提交提案──▶ proposal ──确认提案──▶ authorized
                                                  │
                            Worker 领取 ──▶ executing
                                                  │
                  ┌───────────────────────────────┼──────────────┐
                  ▼                               ▼              ▼
          awaiting_review                      failed    needs_verification
                  │
             用户验收 ──▶ accepted

任意阶段 ──取消──▶ cancelled
```

**`discussion` 阶段不可能存在作业**：创建作业只有一条代码路径
（`proposals.confirm_proposal`），它要求任务已有当前提案。

## messages

| 列 | 说明 |
|---|---|
| role | `user` / `assistant` / `system`。**表允许三种，公共 API 只写 `user`**：`assistant` / `system` 只能由服务端内部写入（见 04 文档「消息角色」） |
| daily_ack_auth | 若这条消息正是当天「每日首次确认」的落点，记录当时所用授权行 id；其余为 NULL |

## proposals

| 列 | 说明 |
|---|---|
| version | 每任务内自增，唯一约束 `(task_id, version)` |
| capabilities | JSON 数组，必须是 `capabilities.py` 里登记过的名字 |
| project_root | 提交时的项目目录快照（授权绑定这个值） |
| digest | 规范化摘要（键排序 + 紧凑 JSON 的 sha256） |
| status | `pending` / `confirmed` / `superseded` |

`digest` 覆盖版本、目标、范围、能力清单、完成条件、风险说明、项目目录。
内容任何实质变化 → 新版本 → 新摘要。

## authorizations

| 列 | 说明 |
|---|---|
| kind | `proposal_confirm`（点按钮执行）/ `default_consent`（勾选默认同意） |
| proposal_version / proposal_digest | 授权锚定的版本与内容指纹 |
| project_root / capabilities | 授权范围 |
| source | `ui_button` / `ui_checkbox` / `api` —— 记录来源便于审计 |
| invalidated_at / invalidated_reason | 非空即失效 |

失效原因目前有：`proposal_superseded_by_v<N>`、`superseded_by_new_consent`、`manual_revoke`。

> ⚠️ 曾经的 `last_daily_prompt_on` 列已删除（schema v2）。每日确认是**系统级**状态，
> 不该挂在任务级授权行上，否则同一天不同任务会各弹一次。现在见 `daily_acks`。

## daily_acks

**每日确认的全局状态。整个 Aevora 每个自然日最多一行。**

| 列 | 说明 |
|---|---|
| day | **主键**，`YYYY-MM-DD`（所有者时区）。主键即去重手段，一天插第二次是 no-op |
| authorization_id | 触发这次确认的默认同意（审计用，可空——授权可能之后被撤销） |
| task_id / project_id | 当次确认发生在哪个任务/项目（审计用，不参与判定） |
| source | `ui_dialog` |
| confirmed_by / confirmed_at | 谁在什么时候确认的 |

为什么独立成表：授权是**任务级**对象，「今天是否已确认」是**系统级**状态，
两者生命周期完全不同。混在一起 → 一天被问多次；也便于将来做「今天确认过就不打扰」的跨项目记忆。

## jobs

| 列 | 说明 |
|---|---|
| idempotency_key | 唯一。值为 `<proposal_id>:<digest>`，同一提案不会重复入队 |
| status | `queued` / `leased` / `running` / `succeeded` / `failed` / `cancelled` / `needs_verification` / `not_implemented` |
| attempt / max_attempts | 领取次数与上限 |
| lease_owner / lease_until / heartbeat_at | 租约。过期 → `needs_verification`，**不自动重排** |
| recovery_point | JSON，执行器上报的恢复点（首版只有 `stage` / `executed`） |
| cancel_requested | 0/1。`queued` 状态取消可直接落 `cancelled` |

`not_implemented` 是首版的正常终态：执行器没接，作业必须如实标记，
不能伪装成 `succeeded` 或 `failed`。

## job_verifications

**v5 新增。`needs_verification` 的出口——没有它，这个状态就是死胡同。**

| 列 | 说明 |
|---|---|
| job_id | 归属作业。**没有 UNIQUE**：同一作业可以有多条（改判） |
| from_status | 核实前的状态：`needs_verification`，或上一轮核实产生的终态 |
| to_status | `succeeded` / `failed` / `cancelled`，由 verdict 决定，不接受自由文本 |
| verdict | `ok` / `not_ok` / `void` |
| verifier | **恒 `local-unverified`**。没有身份校验就写 `owner`，等于把结论提前写进事实字段 |
| note | 人的结论。DB 层 `CHECK (length(trim(note)) >= 4)`——空备注的核实记录等于没有记录 |
| evidence | JSON 数组，至少一项：产物 id / rel_path / 输出摘要 |
| created_at | UTC ISO-8601 |

三条不变量：

1. **只增不改**：没有 UPDATE / DELETE 的代码路径，接口也只有 POST 与 GET；
2. **`jobs.status` 永远等于最新一条**（按 `created_at, rowid` 取最后一条）；
3. **`result_summary` 不被核实覆盖**：那是执行器对"发生了什么"的原始陈述，
   核实者的结论只进 `note`，两者混写之后就分不清哪句是跑出来的。

改判次数 = 记录数 − 1（首条是结案，不是改判）。

## artifacts

**v3 新增。文件本体不在库里，只登记元数据。**

| 列 | 说明 |
|---|---|
| project_id | 必填，归属项目 |
| task_id | 可空。空 = 项目级文件（落在 `_unassigned/` 下） |
| job_id | 可空。**当前恒为空**：执行器未接入，没有作业产物；字段为将来预留 |
| filename | 展示用文件名，已过 `security.sanitize_filename` 白名单 |
| rel_path | **项目内相对路径**：相对 `<产物根>/<项目名>/`，POSIX 分隔符 |
| content_type | 只保留 `type/subtype`，参数（charset 等）丢弃；不合法则 `application/octet-stream` |
| kind | `upload`（当前唯一写入路径）/ `job_output`（预留，暂无写入方） |
| size_bytes | 实际写入字节数（不是 Content-Length） |
| sha256 | 写盘时边写边算，与文件内容一致 |
| storage_path | 服务端绝对路径。**任何接口都不返回**，只用于自己拼盘 + 下载前校验 |
| created_at | UTC ISO-8601 |

落盘形状：

```
<AEVORA_ARTIFACTS_DIR>/<项目名>/<task_id 或 _unassigned>/<YYYY>/<MM>/<DD>/<产物 id>__<文件名>
```

四条约束：

1. **路径由服务端生成**。客户端只给文件名，给不了目录、也给不了绝对路径；
   名字里带 `/`、`\`、控制字符、或是 `.` / `..` 一律 422。
2. **先写文件、后写库**。写库失败就删文件；写文件中途失败就删 `.part` 临时文件。
   顺序反了会留下"库里说有、磁盘上没有"的记录。
3. **下载时再校验一次** `storage_path`。库被手改成 `/etc/passwd` 也只是 403，
   不会真的把系统文件发出去。
4. 物理位置与项目工作目录（`projects/<name>`）**分开**：工作目录将来是执行器的
   读写区，产物混进去会被误当成"待处理输入"。

## events

| 列 | 说明 |
|---|---|
| seq | `INTEGER PRIMARY KEY AUTOINCREMENT`，单调且不复用 |
| type | 白名单，见 `app/events.py::EventType` |
| payload | JSON，`sort_keys=True` 便于比较 |
| project_id / task_id | 可为空（全局事件）；**不设外键**，审计记录不随业务对象删除而消失 |

游标补读：`GET /api/events?after=<seq>`；实时推送：`GET /api/events/stream?after=<seq>`。

## 首版没有的表

- `project_states`（独立的项目状态对象）—— 首版用 `projects.current_summary` 承载
- 用户 / 会话 / 设备表 —— 首版单所有者，无鉴权
